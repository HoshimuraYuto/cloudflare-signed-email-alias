# Cloudflare Signed Email Alias

[English](README.md) | 日本語

Cloudflareの公式プロジェクトではありません。

サイトごとに専用のメールアドレスを作り、そのアドレスに届いたメールを自分の受信箱へ転送するCloudflare Workerです。アドレスは、パスワードマネージャーがaddy.io互換のAPIを呼んで作ります。Workerは何も保存しません。アドレスそのものに署名が入っていて、署名が正しいメールだけを受け取ります。

## 仕組み

- アドレスは`amazon.k7q2.x3m9p0ab@example.com`の形です。先頭からサイト名、ランダムな文字列、署名鍵で作った署名が並びます。
- 署名が正しいアドレスに届いたメールは、そのドメイン用の受信箱へ転送されます。それ以外のメールは受け取りを拒否します。
- 1回のデプロイで、複数のエイリアス用ドメインを扱えます。ドメインごとに受信箱とAPIのホスト名があり、APIのホスト名ごとに、そのドメインのアドレスだけを作れます。
- アドレスを作るAPIはCloudflare Accessで守られています。通るのは、自分のサービストークンを付け、自分のZero Trust組織に登録した端末から送ったリクエストだけです。そのうえで、WorkerもAccessのトークンを確かめ直します。

## 必要なもの

- **受信メールをエイリアス専用にできる、Cloudflare上のドメイン（1つ以上）**
  - このドメインに届くメールはすべてこのWorkerが受け取るため、ほかのサービスでは受信できなくなります。
  - ドメインのキャッチオールルールがすでに別の宛先に向いている場合、デプロイは途中で止まります。
  - メールの受信以外は、これまでどおり使えます。ウェブサイトの公開、ほかのDNSレコードの追加、別のサービスからのメール送信もできます。送信には、そのサービスのSPFの設定を、Email Routingが追加するSPFレコードにまとめる必要があります。
- Zero Trustを有効にしたCloudflareアカウント（無料プランで足ります）。
- 接続先のサーバーURLを指定できるaddy.io連携を持つパスワードマネージャー（Bitwardenなど）。Bitwardenのウェブ保管庫からは使えません。ブラウザが送るプリフライトリクエストを、Accessが拒否するためです。
- デプロイに使う、macOSかLinuxのパソコン。`openssl`が必要です。
- [mise](https://mise.jdx.dev/)。このリポジトリで指定している版のNode.js、pnpm、OpenTofuを入れます。

## 最初に一度だけ行う準備

次の値は、それぞれパスワードマネージャーに保存してください。デプロイのときにそこから読みます。

1. **署名鍵**。次のコマンドで作ります。

   ```sh
   openssl rand -base64 32
   ```

   この鍵は必ず保管してください。これまでに作ったすべてのアドレスがこの鍵に依存しています。鍵をなくすと、すべてのアドレスでメールが届かなくなります。同じ鍵でデプロイし直せば、また届くようになります。

2. **APIトークン**。デプロイと削除のときだけ使います。メールの転送やアドレスの作成には使いません。Cloudflareのダッシュボードで**アカウントの管理** → **アカウントAPIトークン** → **トークンを作成** → **カスタムトークンを作成**を開きます。権限はブロックごとに範囲を1つ選び、ブロックにはその範囲で使える権限だけが表示されます。次の2つのブロックを作ります。

   | ブロックの範囲                                     | グループ                    | 権限                                                        |
   | -------------------------------------------------- | --------------------------- | ----------------------------------------------------------- |
   | アカウント全体                                     | Developer Platform          | Workers Scripts (legacy): Edit                              |
   |                                                    | Cloudflare One / Zero Trust | Access: Apps: Edit                                          |
   |                                                    | Cloudflare One / Zero Trust | Access: Policies: Edit                                      |
   |                                                    | Cloudflare One / Zero Trust | Access: Service Tokens: Edit                                |
   |                                                    | Cloudflare One / Zero Trust | Access: Organizations, Identity Providers, and Groups: Read |
   |                                                    | Cloudflare One / Zero Trust | Zero Trust: Edit                                            |
   |                                                    | Email & Messaging           | Email Routing Addresses: Edit                               |
   | エイリアス用のドメインだけ（**ポリシーを追加**で） | DNS & Zones                 | Zone: Read                                                  |
   |                                                    | DNS & Zones                 | DNS: Edit（`DMARC_POLICY`を使うときだけ）                   |
   |                                                    | DNS & Zones                 | Zone Settings: Edit                                         |
   |                                                    | Email & Messaging           | Email Routing Rules: Edit                                   |

   同じ画面の下のほうで、トークンをさらに絞ります。
   - **TTL**：デプロイする予定の期間にします。デプロイや削除をまた行うときは、トークンを作り直してください。トークンが表示されるのは、作成したときの1回だけです。
   - **クライアントIPアドレスのフィルタリング**：デプロイに使う接続元のアドレスにします。設定した場合は、次の2点に注意してください。
     - デプロイと削除を実行する間は、WARPを切断してください。Gatewayのプロキシがオンだと、コマンドの通信がCloudflare経由で出ていくため、許可していないアドレスからの通信として拒否されます。
     - 接続元のアドレスが変わると、トークンは有効なままでも、アカウントへの操作がすべて`401 Authentication error`で失敗します。IPv6のアドレスは、再起動などで変わることがあります。新しいアドレスをフィルタリングに追加してください。

3. **stateのパスフレーズ**。16文字以上で決めます。OpenTofuが作ったものを記録するファイル（state）を暗号化します。このファイルにはサービストークンも入ります。

## デプロイ

```sh
mise trust
mise install
pnpm install
pnpm run deploy
```

`pnpm run deploy`は設定を環境変数から読みます。秘密の値は、パスワードマネージャーのCLIで取り出して環境変数に入れてください（1Passwordなら`op run`、Bitwarden Secrets Managerなら`bws run`）。ファイルには書かないでください。

| 変数                    | 値                                                                                                                      |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `CLOUDFLARE_API_TOKEN`  | 準備の手順2で作ったAPIトークン                                                                                          |
| `CLOUDFLARE_ACCOUNT_ID` | CloudflareのアカウントID                                                                                                |
| `SIGNING_KEY`           | 準備の手順1で作った署名鍵                                                                                               |
| `STATE_PASSPHRASE`      | 準備の手順3で決めたパスフレーズ                                                                                         |
| `FORWARD_TO`            | エイリアス用のドメインと、そのメールを受け取る受信箱。例：`example.com=you@example.net`。複数のドメインはカンマで区切る |
| `API_SUBDOMAIN`         | 任意。各ドメインに作るAPIのホスト名。既定は`email-alias-api`で、`email-alias-api.example.com`のようになる               |
| `STATE_FILE`            | 任意。暗号化したstateの保存先。既定は`~/.local/state/cloudflare-signed-email-alias/terraform.tfstate`                   |
| `REVOKED_ALIASES`       | 任意。メールを受け取らなくするエイリアス。カンマで区切る。[エイリアスの無効化](#エイリアスの無効化)を参照               |

このコマンドは、Workerをデプロイしたあと、Cloudflareに加える変更を表示して承認を待ちます。承認すると変更を反映し、最後にAccessの値をWorkerに渡します。設定を変えたときは、もう一度実行してください。何度実行しても問題ありません。

出力には、エイリアス用のドメインと受信箱がそのまま表示されます。バグ報告などで人に見せるときは、これらを伏せてください。

### アカウントに1つしかない設定

次の設定は、Zero Trustのアカウントやドメインに1つしかないため、ほかのプロジェクトがすでに使っていることがあります。デプロイがこれらを変えるのは、変数を`true`にしたとき（`DMARC_POLICY`はポリシーを指定したとき）だけです。設定しない場合は、自分で設定してください。

| 変数                       | 設定したときの動き                                                                                                                  |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `MANAGE_DEVICE_ENROLLMENT` | `ENROLL_EMAILS`のアドレス（カンマ区切り）に端末の登録を許可するポリシーを足す。既存のポリシーは残る。アドレスがなければ登録を閉じる |
| `MANAGE_DEVICE_PROFILE`    | 既定のデバイスプロファイルのSplit Tunnelを、Includeモードで、このプロジェクトのホストだけにする                                     |
| `MANAGE_GATEWAY_PROXY`     | **Secure Web Gatewayによるトラフィックのプロキシを許可する**（TCP）をオンにする。APIの端末チェックに必要                            |
| `DMARC_POLICY`             | 各エイリアス用ドメインに、このポリシー（`none`・`quarantine`・`reject`）のDMARCレコードを作る                                       |

- デプロイは、これらの設定の元の値を記録します。`RESET_SHARED_SETTINGS=true`を付けて削除すると、記録した値に戻します。
- `MANAGE_DEVICE_PROFILE`はSplit Tunnelを置き換えます。除外（Exclude）モードで使っていた場合、WARPを通るのはこのプロジェクトのホストだけになります。ほかの通信もWARPに通す必要があるときは、設定しないでください。
- `DMARC_POLICY`は、DMARCレコードがすでにあるドメインがあれば、デプロイを止めます。そのドメインからメールを送らないなら、`reject`にしてください。他人がそのドメインを名乗ってメールを送れなくなります。
- 一度デプロイで管理した設定は、変数をそのままにしてください。外すと設定が削除されてしまうため、デプロイは実行を止めます。

### 初めてデプロイしたあと

上の変数をすべて設定した場合、残る作業は次の3つです。

1. **受信箱を確認する**。`FORWARD_TO`のそれぞれの受信箱に、Cloudflareから確認メールが届きます。メールの中の**Verify email address**を押すまで、転送は始まりません。
2. **各端末を登録する**。
   - WARP（Cloudflare One Client。モバイルではCloudflare One Agent）を入れます。
   - **Zero Trust security**を選び、チーム名を入力します。チーム名は、`<team>.cloudflareaccess.com`の`<team>`の部分です。
   - メールに届くワンタイムPINでログインします。
3. **登録を閉じる**。すべての端末を登録し終えたら、`ENROLL_EMAILS`を空にして`pnpm run deploy`をもう一度実行します。
   - 登録済みの端末はそのまま使えます。新しい端末は登録できなくなります。
   - 閉じないままだと、サービストークンと、受信箱に届くワンタイムPINの両方を手に入れた人が、自分の端末を登録してアドレスを作れます。
   - あとで端末を足すときは、`ENROLL_EMAILS`をまた設定して登録し、終わったら空に戻します。

WARPをつないでいるのにChromeで403（Forbidden）が続く場合は、`chrome://settings/security`でセキュアDNSの設定を確かめてください。

- オフにするか、Cloudflare以外の事業者を選びます。
- OSのDNSをCloudflare（`1.1.1.1`）にしている場合は、「現在のサービスプロバイダを使う」も選ばないでください。ChromeもCloudflareのDNS over HTTPSを使うことになります。
- 設定を変えたら、Chromeを再起動してください。

WARPは、APIの名前解決を見て初めて、APIへの通信をトンネルに通します。ChromeがCloudflareのDNS over HTTPSで行う名前解決は、WARPから見えません。この問題が出るのは主にデプロイ直後の数分間です。アドレスを作れるようになったら、セキュアDNSの設定は元に戻してかまいません。

#### 自分で行う設定

変数を設定しなかった設定は、次のとおり自分で行ってください。

- **端末の登録**（`MANAGE_DEVICE_ENROLLMENT`）：**Zero Trust** → **チームとリソース** → **デバイス** → **管理**タブ → **デバイス登録権限** → **管理**を開きます。自分のメールアドレスを含めるポリシーをアクション「許可」で追加して、保存します。
- **Split Tunnel**（`MANAGE_DEVICE_PROFILE`）：出力`warp_include`に表示されたホストを、デバイスプロファイルのSplit Tunnelに追加します。これらのホストへの通信をWARPに通していない端末からは、APIを使えません。
- **Gatewayのプロキシ**（`MANAGE_GATEWAY_PROXY`）：**Zero Trust** → **Traffic controls** → **トラフィックの設定**を開き、**Secure Web Gatewayによるトラフィックのプロキシを許可する**をTCPでオンにします。オフのままだと、登録した端末からでもAPIは403を返します。

## パスワードマネージャーの設定

Bitwardenで**パス生成** → **ユーザ名**を開き、**タイプ**を**転送されるメールエイリアス**、**サービス**を**Addy.io**にして、次のように入力します。

| 項目                     | 値                                                                                            |
| ------------------------ | --------------------------------------------------------------------------------------------- |
| API キー                 | `pnpm run service-token`の出力                                                                |
| メールアドレスのドメイン | 自分のエイリアス用ドメインの1つ（`example.com`は自分のドメインに読み替える）                  |
| 自己ホスト型サーバー URL | そのドメインのAPIのホスト名（例：`https://email-alias-api.example.com`。末尾に`/`を付けない） |

`pnpm run service-token`に必要なのは`STATE_PASSPHRASE`だけです（`STATE_FILE`を設定した場合はそれも）。

別のエイリアス用ドメインでアドレスを作るときは、この2つの項目をそのドメインのものに書き換えてください。

アドレスは、ログインアイテムの編集画面から作ってください。アイテムに登録したウェブサイトのドメインが、アドレスの先頭に入ります。パス生成のタブから作ったアドレスは、先頭が`mail`になります。

### サービストークンの入れ替え

サービストークンが漏れたおそれがあるときは、次のコマンドで入れ替えます。

```sh
pnpm run rotate-service-token
```

デプロイと同じ環境変数を使います。古いトークンはすぐに使えなくなります。`pnpm run service-token`の新しい出力を、パスワードマネージャーに入れ直してください。

### エイリアスの無効化

スパムが届くようになったエイリアスは、`REVOKED_ALIASES`に加えて`pnpm run deploy`をもう一度実行します。

- そのアドレスあてのメールは、存在しないアドレスと同じように拒否されます。
- 一覧から外してもう一度デプロイすれば、また受け取れます。

## 削除

```sh
pnpm run destroy
```

- `SIGNING_KEY`と`ENROLL_EMAILS`以外は、デプロイと同じ環境変数を使います。
- 確認のためにすべてのエイリアス用ドメインを入力すると、Workerと、デプロイでこのプロジェクトのために作ったものをすべて削除します。
- アカウントに1つしかない設定とDMARCレコードは、ほかのプロジェクトが使っているかもしれないので残します。これらも元に戻すときは、`RESET_SHARED_SETTINGS=true`を付けてください。
  - Split TunnelとGatewayのプロキシは、デプロイで初めて管理したときに記録した値に戻ります。記録したSplit Tunnelがこのプロジェクトのホストと同じだった場合は、自分で戻してください。
  - デバイス登録権限は、元のポリシーに戻ります。アプリそのものは残します。
- 自分で削除する必要があるものは、最後に一覧で表示されます。

## 開発

```sh
mise trust
mise install
pnpm install
tofu -chdir=infra init -backend=false
pnpm check
```

`pnpm check`は、フォーマットとリントの確認、型チェック、すべてのテストを実行します。

- Workerのテストはworkerdで、スクリプトのテストはNode.jsで、`tofu test`は偽のプロバイダーで動きます。
- ネットワークにも認証情報にも頼りません。

`pnpm fix`は、フォーマットとリントの自動修正をかけます。

Workerのテストは`test/`に、スクリプトのテストは`scripts/`のスクリプトの隣に置いています。2つは動く環境が違うため、それぞれに`tsconfig.json`と`vitest.config.mts`があります。
